# 商品分类规则与维护说明

本文件说明 `product-map.json` 的组织方式、分类规则、已知陷阱，以及如何维护它。
**本文件不含任何价格。价格永远来自实时菜单。**

> 价格字段的语义（尤其是「菜单现价可能是条件价」）单独记录在
> `references/menu-price-semantics.md` —— 那里有 26 个条件价商品的逐一裸核价证据
> （午餐 16 条 + 早餐 10 条，门店 `3230019`），以及内核采用的预筛规则。
>
> ⚠️ **`discountType` 是时段级属性，不是商品固有属性**：同一商品 `510479 燕麦奶铁`
> 午餐时段是 `随单购麦金卡优惠`，早餐时段是 `随单购早餐卡优惠`。
> 因此映射/核价证据必须带 `storeCode` + `daypart`，**不可跨时段复用绝对价格**。

## 一、为什么不能靠商品名称分类
这是本项目用真实 MCP 调用换来的结论，不是推测。

| 现象 | 实测证据 |
|---|---|
| 名称不含"堡"但实际含汉堡 | `9900015183 精选单人餐三件套`，默认组成是 板烧鸡腿堡 + 中薯条 + 可乐中杯 |
| 名称像正餐套餐但完全不含汉堡 | `9900011126 酥脆无双套餐`（炸鸡+迷你薯条+可乐）、`9900011123 "辣"么快乐套餐`（鸡翅+麦乐鸡+可乐）、`9900004835 麦乐鸡套餐`（麦乐鸡+薯条+可乐） |
| 同价同类的两个套餐默认组成不同 | `9900015187 人气经典随心配` 与 `9900015188 精选超值随心配` 同为 ¥14.9，前者蓝区默认为双层吉士汉堡，后者默认为咖喱肉骨鸡 |
| 菜单名与详情名不一致 | `9900004835` 菜单显示"麦乐鸡套餐"，`query-meal-detail` 返回"麦乐鸡经典中套餐" |
| 套餐子项编码与顶层菜单编码不同源 | 套餐内"可乐中杯"=`3050`，顶层"可乐"=`9900008751`；套餐内"小薯条"=`4800`，顶层"中薯条"=`4810`（也有同源的，如 `4810` 两边都是中薯条） |

**结论：以 `code` 为主键；名称只用于展示和兜底分类。**

## 二、唯一可靠的结构判别器

对任意商品调用 `query-meal-detail`，看 `data.rounds`：

| `rounds` | 含义 | 实测例 |
|---|---|---|
| `[]` 空数组 | **原子商品**，商品名即组成 | `1450 麦香鸡`、`1406 板烧鸡腿堡`、`1440 麦辣鸡腿汉堡`、`1120 双层吉士汉堡` |
| 非空 | **组合商品**，必须看默认子项 | `9900015160 大堡口福三件套`（3 轮）等 |

组合商品的几种形态（均已实测）：

| 形态 | 特征 | 例 |
|---|---|---|
| 固定组合盒 | 多轮，每轮仅 1 个选项 | `9900016076` 鸡薯双全盒（3 轮） |
| 单选套餐 | 1 轮，多选项且全是同类 | `9900015162` 牛肉堡单品精选（汉堡包 / 吉士汉堡包） |
| 标准套餐 | 主食 + 小食 + 饮料 | `9900015160`、`9900015183` |
| 双区自选 | 2 轮「蓝区 / 粉区」 | `9900015187`、`9900015188` 随心配 |
| 儿童餐 | 4–5 轮，含玩具等非食品项 | `9900016054 汉堡开心乐园餐` |

## 三、置信度分级

`verifiedProducts` 里的每个商品都有 `confidence` 字段：

| 值 | 含义 | 能否满足「必须含汉堡」 |
|---|---|---|
| `confirmed_detail` | 已用 `query-meal-detail` 实测确认组成 | **可以** |
| `name_inferred_single` | 名称兜底分类（未逐条调 detail） | **不可以**，只能满足可选偏好 |
| `unknown` | 未分类 | **不可以** |

`scripts/plan.py` 用 `canSatisfyBurgerConstraint` 字段落实这条纪律：

```python
"canSatisfyBurgerConstraint": bool(rec.get("containsBurgerByDefault"))
# 名称推断的商品恒为 False —— 这是代码级保证，不是约定
```

## 四、名称兜底规则（atomicNameRules）

仅作用于**未列入 `verifiedProducts`** 的商品。规则自上而下匹配，先命中先返回。

| 顺序 | 分类 | 匹配方式 | 关键词 |
|---|---|---|---|
| 1 | `exclude` | **suffix** | `酱` |
| 2 | `exclude` | contains | `玩具` `徽章` `帽` `贴` `捶` `痒痒挠` `餐具` `周边` |
| 3 | `drink` | contains | `可乐` `雪碧` `雪冰` `咖啡` `美式` `奶铁` `拿铁` `卡布奇诺` `牛奶` `燕麦奶` `苹果汁` `果汁` `橙橙` `柠柠` `红茶` `绿茶` `豆浆` `怡泉` `阿芙佳朵` `朱古力` `黑巧` `抹茶` |
| 4 | `side` | contains | `薯条` `薯格` `麦乐鸡` `鸡块` `鸡翅` `V翅` `炸鸡` `脆汁鸡` `肉骨鸡` `鸡柳` `鸡米花` `芝士条` `薯饼` `派` `苹果片` `玉米杯` `麦旋风` `新地` `圆筒` `鸡排` `趣鸡球` `多多笋卷` `叠叠卷` `沙拉` |
| 5 | `burger_name_inferred` | contains | `汉堡` `堡` `麦香鸡` `巨无霸` `板烧`（**仅作标注，不进入硬性条件候选池**） |

### 已踩过的两个坑（都有回归测试）

1. **`酱` 必须用 suffix 匹配。** 用 contains 会把「蘸酱炸鸡」「蘸酱麦麦脆汁鸡」「蘸酱BFF四宫格小食盘」这些**真实餐品**误排除。
2. **`side` 必须包含 `炸鸡`。** 否则「蘸酱炸鸡」会掉进"未知"，被静默丢掉。
3. **刻意不写泛化的「鸡」。** 那会把汉堡类的「麦香鸡」误判成小食。

回归断言在 `scripts/plan.py selftest` 里，共 21 项。

## 五、如何维护映射表

### 补齐某个商品

```bash
# 1. 用官方 MCP 查详情（到店渠道，storeCode 用当前门店）
#    query-meal-detail(storeCode, orderType=1, beType=1, code=<商品编码>)

# 2. 把结果按已有格式写进 references/product-map.json 的 verifiedProducts
#    必填：nameFromMenu / nameFromDetail / kind / roundsVerified / roundsLen /
#          defaultComposition / categories / containsBurgerByDefault /
#          burgerSwitchable / confidence / evidence
```

### 判定 `containsBurgerByDefault` 的规则

看每个**必需轮次**（`minQuantity >= 1`）里 `isDefault = 1` 的子项：

- 全部必需轮次的默认子项里**存在汉堡** → `true`
- 默认子项里**没有汉堡** → `false`（即使存在可换成汉堡的选项，第一版也不认）
- 默认含汉堡但同轮可换成非汉堡 → 仍为 `true`，同时置 `burgerSwitchable = true`，输出时要提示"默认含，可切换"

### 什么时候必须重新核验

- `detailVerifiedAt` 距今较久（建议超过 30 天）
- 实时菜单里该编码消失或名称变化
- 该商品促销/换季调整（套餐内容可能被改）

**重新核验后必须更新 `evidence.at` 和 `detailVerifiedAt`。**

### 编码从在售清单消失时的标准处置（2026-10-16 确立）

不要凭一次 `60001` 就动手改映射表。按顺序取证：

1. `query-meals` 拉当前时段全量菜单 → 该编码在不在 `data.meals`？
2. 在售清单里有没有**同名**（或同名同价）的新编码？
3. 若有 → 对**新编码**调 `query-meal-detail`，把轮次名、默认项**逐项**与旧条目比对：
   - 逐项一致 → 记 `equivalence = "A"`（仍要**独立建条目**，不得复制粘贴旧结论）
   - 有差异 → 记 `equivalence = "B"`，并在新条目写 `equivalenceWarning`
4. 若没有同名替代 → 再判断是否**时段限定**（该编码是否只在别的时段快照里出现过）。
   缺原时段证据时记 `equivalence = "C"（当前不可验证）`，**不得**判定已下架。
5. 旧编码统一标 `retired`（保留组成与 evidence，只加轮换元数据），
   由 `build_pool` 强制排除；**没有任何一种情况允许删除历史条目**。

### ⚠️ 「堡」包含鱼堡 —— 蛋白类型需明示

菜单分类「巨无霸／**牛鱼肉堡**」把牛、鱼、肉同列为「堡」，因此
`双层深海鳕鱼堡`、`鱼排堡` 这类**鱼堡也算汉堡**，可用于满足「必须含汉堡」。

但本 Skill **不支持**「只要牛肉堡 / 不要鱼堡」这类蛋白偏好筛选。
第六批新增条目因此带了**纯标注**字段 `proteinType`（beef / fish）：
它**不参与任何判定**（`plan.py` 从不读取，有测试断言），只为将来做偏好筛选预留可读信息。
若用户提出蛋白偏好，必须如实说明当前无法据此筛选，不得假装已支持。

### ⚠️ `requiresUserSelection` —— 新增的安全标记

`9900004066 堡堡随心拼（7件任选）` 的三个 round **全部是 multi-select**
（`minQuantity = maxQuantity = 2 / 3 / 2`，共 7 件），默认虽选中 2 份麦辣鸡腿汉堡，
但第 1 轮含「酥酥多笋卷」等非汉堡选项。用户完全可以选出不含汉堡的组合。

因此该条目：

- `containsBurgerByDefault = true`（如实记录默认组成）
- `requiresUserSelection = true`
- 代码层强制 `canSatisfyBurgerConstraint = false` —— **不得**用于满足"必须含汉堡"
- `kind = "combo_multi_select"`

**后果**：预算搜索结果偏向"已确认"的那批商品，可能漏掉更优搭配。这是刻意的保守取舍 —— 宁可少推，不可错推。

**注意**：这**不构成**"整个菜单无解"的证明。输出无解结论时必须带上这句免责说明。

### 随时生成待核实清单（只读）

```bash
python3 scripts/plan.py coverage \
  --menu tests/fixtures/menu_plan_fixture.json \
  --map references/product-map.json --out /tmp/mcd_coverage.json
```

该命令**只报告缺口，不修改映射表**（有测试断言映射表在体检前后字节一致）。
输出字段：`priorityToVerify[]`（名称疑似含汉堡但组成未核实，含 `code` / `name` / 菜单价）、
`verifiedNotInMenu[]`（映射表里有、但当前菜单找不到的条目，用于发现过期条目）。
**补齐前不得把它们当作含汉堡候选**，也不得仅凭名称写回映射表。

### ⚠️ 核实时段陷阱（2026-10-16 实测）

麦当劳菜单**随时段整体切换**（早餐 / 午餐 / 下午茶 / 夜市 / 宵夜）。
2026-10-16 10:00 时在门店 `3230019`（早餐时段 05:14–10:15）对常规商品调用
`query-meal-detail`，**全部返回 `60001 未匹配到商品，请重新拉取全量商品列表`**。

**这不是商品不存在，也不是映射表失效。** 正确做法：

1. 换到当前处于常规时段的门店（本次用的是 `3230442`，午餐时段 09:14–14:15），或
2. 等到本店常规时段再查。

**代价**：同一商品在不同门店**价格不同、部分编码也不同**，所以跨店只能核实"组成"，
**不能**跨店搬用核价结果。已核实批次的门店记录在各自 `evidence.storeCode` 里。

### ⚠️ 编码轮换陷阱（2026-10-16 实测并已处理）

**商品编码不是永久的。** 菜单换季/换活动时，同一商品会换新 code。
2026-10-16 菜单从早餐切到午餐（10:47:45）后实测，7 个编码被替换：

| 已下架编码 | 名称 | 当前在售编码 | 等价性 | 依据 |
|---|---|---|---|---|
| `9900015162` | 牛肉堡单品精选 | `9900008747` | **A（默认组成等价）** | roundsLen/轮次名/默认项逐项一致 |
| `9900015164` | 鸡肉堡单品精选 | `9900008746` | **A** | 默认仍为 515295 双层脆鸡堡 |
| `9900016054` | 汉堡开心乐园餐 | `9900016057` | **A** | 5 个轮次名与默认项逐项一致 |
| `9900015183` | 精选单人餐三件套 | `9900004064` | **A** | 默认仍为 1406/4810/3050 |
| `9900015160` | 大堡口福三件套 | `9900015602` | **B（不等价）** | 默认主食 515295 → 521147 |
| `9900015187` | 人气经典随心配 | `9900013304` | **B（不等价）** | 粉区默认 515281 → 521328 |
| `9900015188` | 精选超值随心配 | `9900015568` | **B（不等价）** | 两轮默认项均已变 |

另有 2 个编码**只记录、不定级**：`9900015165 派` 有同名同价新编码 `9900008752` 但未比对结构；
`521337 鲜萃冰咖` 只在套餐子项里出现，无顶层替代编码。

**同名同价不能单独证明等价** —— 上表里 3 个 B 级案例正是"同名甚至同价，但默认组成已经变了"。

**因此 `60001` 有三个成因**，必须先区分：

1. **时段**：该商品在当前时段整体不供应 → 换时段或换门店。
2. **编码轮换**：商品在售但编码换了 → 查 `query-meals` 的 `data.meals` 确认新编码。
3. **真失效**：编码既不在菜单、也没有同名替代 → 需按时段证据定级，不得直接删条目。

**纪律（现在已落到代码上）**：

- 遇到 `60001` **不得**直接删除或改写映射表条目；
- **不得**用同名商品的新编码去顶替旧编码做核价 —— 那等于伪造来源；
- 旧编码在映射表里标 `retired`，`build_pool` **强制跳过**（即使菜单里意外重现也不进商品池）；
- 新编码必须**独立核实、独立建条目**（带 `rotationFrom`），**不得**沿用旧条目的组成结论；
- 映射表里"不在售且未标 retired"的条目必须为空 —— 由 `coverage` 的
  `verifiedNotInMenuUnmarked` 字段强制检查（有测试断言）。
- 完整的轮换来源、逐条证据与证据强度见 `product-map.json` 的 `codeRotation` 表。
