# 菜单价格字段语义（menu-price-semantics）

> 本文件回答一个问题：**`query-meals` 返回的 `currentPrice` 到底是不是「买了就付这个价」？**
>
> 答案：**不是总是。** 部分商品的 `currentPrice` 是**条件价**（需随单购麦金卡才成立）。
> 本文件记录字段语义的**证据**、**已验证范围**与**未确认之处**，以及内核据此采用的预筛规则。
>
> 最后更新：2026-10-16（P1.13），证据门店 `3230019`、`orderType=1`、`beType=1`、
> **午餐 + 早餐两个时段**。

> **P1.12 更新摘要**：菜单快照已刷新为 2026-10-16T11:55:12 的 **106 项**，
> 「随单购麦金卡优惠」商品由 13 增至 **17** 个（新增的 `521955 麦当劳联名徽章` 是周边非食品、
> 被 `atomicNameRules` 排除在商品池外，故池内仍为 **16** 个）；
> 裸核价实测证据由 13 条扩到 **16 条**（P1.12 新增 `9900000881`/`9900000882`/`9900006957`，均为 6650 分）。

> **P1.13 更新摘要（跨时段验证）**：用 `reservationDate = 2026-10-17 08:00` 取得门店
> `3230019` 的**真实早餐菜单**，首次观察到 `随单购早餐卡优惠` 这一取值（此前零样本）。
> 实测 **10/10** 裸核价 == `originalPrice` → 白名单扩展为 2 个取值；
> `麦金卡优惠` / `早餐卡优惠`（不带"随单购"前缀）**仍为零样本 → 继续保守**。
> ★ 关键发现：**`discountType` 是时段级属性，不是商品固有属性**
> （`510479 燕麦奶铁` 午餐 `随单购麦金卡优惠` / 早餐 `随单购早餐卡优惠`）。

## 一、字段清单（官方工具定义）

| 字段 | 官方说明 | 是否可信 |
|---|---|---|
| `currentPrice` | 餐品现价（销售价） | ⚠️ **可能是条件价**，见第三节 |
| `originalPrice` | 商品原价（**划线价**） | ⚠️ 语义**依赖 `discountType`**，不能单独使用 |
| `discountType` | 享受优惠的类型：`null`-不享受优惠，`"早餐卡优惠"`，`"促销优惠"`，`"麦金卡优惠"`，`"随单购早餐卡优惠"`，`"随单购麦金卡优惠"` | ✅ 取值的**语义**需逐个验证 |
| `canWithOrder` | 该商品是否可随单购早餐卡或麦金卡 | 仅布尔，不含价格信息 |
| `withOrder` | 「随单购商品，当商品享受随单购优惠价时，用户必须要选择随单购才可享受优惠，**否则将以原价购买**」（`cardId` / `cardType` / `membershipCode` / `specId`） | ✅ 这句话是「原价 = 无条件价」的**官方依据**；但 `withOrder` 结构本身**不足以**推断优惠幅度或门槛 |

**关键官方原话**（`withOrder` 的字段说明）：**「否则将以原价购买」** —— 这是 `originalPrice`
可作为随单购商品无条件价的直接依据。但仅凭这句话还不够（它没说原价一定可解析、也没说
对所有 `discountType` 都成立），所以又做了下面的实测。

## 二、本地菜单里的真实分布（`tests/fixtures/menu_plan_fixture.json`，106 项）

| `priceStatus` | 数量 | 含义 |
|---|---|---|
| `menu_price_is_effective` | **86** | 无 `discountType` 声明 → 菜单现价即销售价 |
| `conditional_price_replaced_by_original` | **17** | `discountType = 随单购麦金卡优惠` → 菜单现价是条件价 |

## 四、内核采用的预筛规则（`scripts/plan.py`）

`resolve_price_semantics(info)` 返回 `prefilterPriceYuan`（本地预算预筛价）与 `priceStatus`：

| `discountType` | `priceStatus` | 预筛价 | 依据 |
|---|---|---|---|
| 缺失 / `null` | `menu_price_is_effective` | `currentPrice` | 行为与修复前一致；对照实测 9900005456 |
| `促销优惠` | `promo_price_is_effective` | `currentPrice` | 对照实测 521986 / 507409 |
| **精确等于** `随单购麦金卡优惠` | `conditional_price_replaced_by_original` | `originalPrice` | 16/16 实测 + 官方「否则将以原价购买」 |
| 其它任何取值（含 `早餐卡优惠`、`麦金卡优惠`、`随单购早餐卡优惠`） | `unknown_price_semantics` | **`None`** | **无证据 → 保守** |
| 缺 `currentPrice` / 条件价缺 `originalPrice` | `unknown_price_semantics` | **`None`** | 缺字段 → 保守 |

**`prefilterPriceYuan = None` 的语义是「不得做本地预算判断」**，不是「免费」也不是「0」：

- 不参与本地预算剪枝（**未知 ≠ 超预算**），仍会进入候选；
- 组合带上 `budgetCheckDeferred = true`，`prefilterTotalYuan = null`；
- 预算合规性**只能**由官方 `calculate-price` 判定。

### 为什么可以拿 `originalPrice` 剪枝

预算剪枝只有在「预筛价 > 预算 ⟹ 实付 > 预算」时才成立，因此预筛价必须是**实际价的可靠估计**。
对这类商品，`originalPrice` 不是"上界"也不是"下界"，而是**实测等于实际价**（16/16）。
所以它既能剪枝，也不会把预算内的组合误剪掉。

反过来，用 `currentPrice`（¥28）剪枝则严重失真：会把实付 ¥58 的商品当成 ¥28 选进 ¥35 的预算里。

### 已知的残余风险（诚实记录）

- 结论只在 `3230019` 午餐时段验证过。**不得据此推广到其他门店/时段。**
- 若换门店后 `originalPrice < 实际价`：预筛偏乐观 → 会把超预算组合送去核价 → 由官方
  `over_budget` 兜底，**不会**输出错误价格（安全失败）。
- 若 `originalPrice > 实际价`：预筛偏保守 → 可能漏掉本可负担的组合（完整性损失，非正确性错误）。
- 两种方向都不会重演「把 ¥58 说成 ¥28」这类**误导性**错误。

## 五、明确**未确认**的部分

1. **`withOrder` 不足以确定优惠条件。** 本店实际值只有
   `{"membershipCode": "106", "specId": "870"}`，没有任何门槛、幅度、有效期信息。
   因此**不能**靠 `withOrder` 反推价格；它只能用于「这是随单购商品」的佐证。
2. **`早餐卡优惠` / `麦金卡优惠` / `随单购早餐卡优惠` 三个官方取值本店菜单里从未出现**，
   语义**未验证**。故意**不做前缀泛化**（不因为「随单购早餐卡优惠」带「随单购」就套用原价）——
   要新增取值，必须先取得该取值下的真实裸核价证据，再加入
   `VERIFIED_CONDITIONAL_DISCOUNT_TYPES` 白名单。
3. **`originalPrice` 的语义依赖 `discountType`**：对随单购商品它等于无条件价，
   对普通套餐它只是远高于实付的划线价（如 9900011056 的 ¥116.5 实际就是实付价、
   而 9900005456 的 ¥47.5 只是划线）。**不允许**在无 `discountType` 的情况下使用它。
4. **本店只有一个时段的样本。** 价格与 `discountType` 都可能随活动/时段变化，
   每次运行都应重新拉菜单；`coverage` 输出的 `priceStatusCounts` 可用来快速核对分布是否变了。

## 六、与其它规则的关系

- **`calculate-price` 仍是唯一价格权威。** 预筛只影响「哪些组合值得送去核价」，不影响报价。
- **菜单价仍如实保留**在 `menuTotalYuan` / `menuUnitPriceYuan`，用于记录
  「菜单价 ≠ 官方价」的差异（`discrepancies[]`）—— 这正是把条件价暴露出来的方式，
  不会因为改用预筛价而被抹掉。
- **条件价商品不会被静默丢弃**：`plan.py candidates` 的输出里有
  `meta.conditionalPriceNotice`（计数 + 逐个原因），以及 `meta.menuPriceAnomalies`
  （缺 `currentPrice` 等无法使用的条目）。

## 七、候选分层：未定价候选不得挤掉可信候选（P1.10）

### 7.1 缺陷（2026-10-16 端到端审计发现）

「未知 ≠ 超预算」要求 `prefilterPriceYuan = None` 的商品**不被本地剪枝**，因此这类组合会
大量进入 `plans`。但 `select_candidates` 只挑 6 个送核价，而**排序与三类代表
（best / richest / cheapest）的选取原先不区分价格可信与否** —— 未定价候选的
`_basis()` 会退回**菜单价**参与竞争，于是：

| 复现方式 | 结果 |
|---|---|
| 把 `9900005456` 的 `discountType` 改成未验证取值，预算 ¥35 | 候选中出现菜单价 **¥54.5**（已超预算）的未定价候选，并**挤掉了原本可行的候选** |
| 同上，预算 ¥10（真实无解） | 注入 1 个未定价商品后可行组合 0 → 8，**6 个席位被未定价候选全部占满**，`noSolutionAdvice` 随之失效（用户看不到"最低 ¥14 差 ¥4"的解释） |
| 全部 36 个锚点都改成未验证 `discountType` | 组合数 78432，6 个席位仍全为未定价候选 |

**后果**：不会输出错误价格（最终价仍由 `calculate-price` 决定），但会
① 浪费核价调用；② 把真正可行的候选挤出核价队列；③ 让无解解释失效。

### 7.2 修复规则

`select_candidates` 现在把候选分两组，**可信组优先占满席位**：

| 分组 | 判据 | 排序基准 | 席位优先级 |
|---|---|---|---|
| `credible` | `prefilterPriceYuan` 非 None | 预筛价（条件价已改用原价） | **优先**，先占满 `max_candidates` |
| `deferred` | `prefilterPriceYuan` 为 None | 菜单价（仅供组内排序） | 仅在**剩余席位**里补齐 |

- 组内仍是「三类代表 + 锚点轮转 + 组内兜底」，去重签名跨组共享（可信组先占）。
- **兜底不跨组** —— 未定价候选不得借兜底挤掉可信候选。
- **不剪枝原则不变**：未定价组合仍在 `plans` 里，只是不再优先占用核价席位。

### 7.3 输出（如实告知，不静默）

- `meta.candidateComposition`：`credibleCount` / `priceDeferredCount`；
- `meta.priceUndeterminedNotice`：当 `credibleCount == 0` 且存在未定价候选时给出 ——
  说明「本地无法先行判断是否超预算」、**「这不等于无解」**，并给出最低已确认汉堡作参考；
- 候选级 `budgetCheckDeferred` 标记保持不变。

### 7.4 仍然存在的代价（诚实记录）

未定价候选不被剪枝，会让 `plans` 规模显著放大（实测 346 → 1505 → 6136 → 78432）。
`MAX_PLAN_GUARD = 400000` 是最后的保险丝。**这是「未知 ≠ 超预算」原则的必然代价**，
刻意不通过剪枝来消除 —— 若要收敛，正确做法是补齐该 `discountType` 的实测证据，
把它从 `unknown` 转为可判定的语义。

## 八、跨时段验证（P1.13）

### 8.1 为什么需要单独验证

P1.9–P1.12 的全部价格证据**只来自 `3230019` 的午餐时段**。而麦当劳的
`discountType` 会随时段变化（早餐卡 vs 麦金卡），所以「原价的语义」是否也只在午餐成立，
此前**没有证据**。直接默认成立 = 猜测。

### 8.2 取得跨时段菜单的方法

`query-meals` 与 `calculate-price` 都支持 **`reservationDate`**（格式 `yyyy-MM-dd HH:mm`）。
门店 `3230019` 全天营业且支持预约，于是用**预约明天早餐时段**取得真实早餐菜单，
**同一家门店** → 排除门店差异干扰。

**⚠️ 必须先证明该参数真的生效**，否则所谓"早餐数据"可能只是换了个时间重跑同一份午餐菜单。
本轮的反证：

| 调用（同一商品 `9900003431 大脆鸡扒麦满分组合`） | 结果 |
|---|---|
| 不带 `reservationDate`（当前午餐时段） | `success:false, code 60006`（商品已售罄或不可售） |
| 带 `reservationDate=2026-10-17 08:00` | `success:true, price 1350` |

→ 菜单确实按时段整体切换，本批是**真实的早餐时段数据**。
