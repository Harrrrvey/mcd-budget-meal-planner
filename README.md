# 麦麦预算点餐师 · McDonald's Budget Meal Planner

> 告诉我预算和想吃什么，我帮你找到符合条件的麦当劳餐品组合，并用官方 MCP 核实价格。

一个基于**麦当劳官方 MCP** 的 WorkBuddy Skill。你在对话里说预算和门店，它去查**实时菜单**、在本地搜索组合、再用官方 `calculate-price` **核价**，最后给你 2–3 个**经过核价**的方案。

**这是一个 Skill，不是网站，不是 Web App，不是点餐平台。** 交互全部发生在 WorkBuddy 对话中。

---

## 解决什么问题

在麦当劳点餐时，"预算 X 元、必须有个汉堡、最好再来杯饮料"这种搭配，靠人翻菜单心算是低效且容易超预算的。
本项目把这个过程交给官方 MCP：**实时菜单 + 官方核价**，所以给出的价格不是估算，而是麦当劳官方接口算出来的。

## 不支持（刻意不做）

外送 / 得来速 / **自动领券（默认关闭）** / 自动下单 / 支付 / 积分 / 会员 / 套餐拆解与特调 / 营养与过敏原筛选 / 多人分餐 / 用户历史 / 独立网页或应用。

> 关于领券：官方 `auto-bind-coupons` **无入参、只能一次性领取全部可领券**，且工具清单中
> **没有退券工具**（不可撤销）。因此本项目默认不领券，只在用户**明确要求并确认**后才执行。

## 安装

### 1. 配置麦当劳 MCP

1. 申请麦当劳 MCP Token（入口见官方仓库 <https://github.com/M-China/mcd-mcp-server>）；
2. 打开 WorkBuddy → 左侧边栏【专家·技能·连接器】→【连接器】→ 右上角【自定义连接器】→【配置MCP】；
3. 粘贴 `mcp-config.example.json` 的内容，把 `${MCD_MCP_TOKEN}` 换成你的真实 Token；
4. 回到【自定义连接器】，把 `mcd-mcp` **启用**。

也可以直接写入 `~/.workbuddy/mcp.json`：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": { "Authorization": "Bearer ${MCD_MCP_TOKEN}" }
    }
  }
}
```

> ⚠️ 本仓库**不含**任何真实 Token。`mcp-config.example.json` 只使用环境变量占位符。

### 2. 安装 Skill

```bash
# 用户级（所有项目可用）
ln -s "$(pwd)" ~/.workbuddy/skills/mcd-budget-meal-planner

# 或项目级
mkdir -p .workbuddy/skills && ln -s "$(pwd)" .workbuddy/skills/mcd-budget-meal-planner
```

### 3. 环境要求

- Python 3.8+（仅用标准库，无第三方依赖）
- 已启用 `mcd-mcp` 连接器

## 工作原理

```
自然语言输入
  → 解析槽位（预算 / 城市 / 门店关键词 / 偏好）
  → query-nearby-stores  → storeCode
  → query-meals          → 实时菜单（价格的唯一来源）
  → 【只读】query-store-coupons + query-my-coupons + available-coupons
       → plan.py coupons  → 区分 已领券 / 本店可用券 / 未领取券
  → plan.py candidates（--coupons）→ 本地组合搜索 + 券-商品编码匹配 + 探针剪枝
  → calculate-price      → 每候选：不带券基线 + 逐券试算
  → plan.py compare      → 原价 / 优惠 / 应付 / 实际节省（= 无券价 − 带券价）
  → 输出 2–3 个已核价方案
```

本地内核 `scripts/plan.py` 是**离线、无副作用**的：不联网、不下单、不支付、不领券。

```bash
python3 scripts/plan.py selftest                                   # 30 项自检
python3 tests/test_plan.py                                         # 1095 项（组合搜索/核价/来源追踪/编码轮换/条件价预筛/候选分层/跨时段/硬约束）
python3 tests/test_coupons.py                                      # 87 项（优惠券）
python3 tests/test_product_map.py                                  # 437 项（商品映射）
python3 scripts/plan.py candidates --help
python3 scripts/plan.py coupons --help
python3 scripts/plan.py compare --help
python3 scripts/plan.py coverage --help                            # 映射表覆盖度体检（只读）
```

## 当前限制（必读）

1. **只支持到店自取**（`orderType=1`, `beType=1`）。外送与得来速未实现。
2. **商品映射表覆盖 49/106 个商品（46.2%）**。其余 **51 个未覆盖** + **6 个明确排除**（周边/玩具/非食品），
   一律被视为"未知组成"，**不会**用于满足"必须含汉堡"。
   覆盖率的历史轨迹（2026-10-16）：47.0%（66 项）→ 33.7%（92 项）→ 45.6%（92 项）→ **46.2%（106 项）**。
   33.7% 那次**不是退步**：菜单快照刷新后条目由 66 涨到 92（旧快照只是子集），分母变大。
   随后分批补齐「名称疑似含汉堡」的商品：第六批 11 个（锚点 25 → 36）、第七批 7 个安格斯厚牛堡系列（36 → **43**），
   **优先核实清单已清空**（`plan.py coverage --menu ... --map ...` 可复现）。
   ⚠️ 剩余未覆盖商品里仍有 `1600 麦香鱼`、`9900005460 麦香鱼套餐` 等名称像堡但未核实的，一律不得作锚点。
3. **菜单随时段整体切换。** 麦当劳在早餐 / 午餐 / 下午茶 / 夜市 / 宵夜之间会整体换菜单，
   常规商品在早餐时段调用 `query-meal-detail` 会返回 `60001 未匹配到商品`。
   这是**时段问题，不是商品不存在**，不得据此判定映射失效。
   实测还发现**菜单切换晚于预约窗口起点**（预约写 10:44 开始，10:44:55 仍是早餐，10:47:45 才是常规菜单）。
4. **商品编码会轮换。** 同一次切换中实测到 **7 个编码被替换**，其中 3 个**同名但默认组成已变**
   （`9900015160→9900015602` 默认主食从双层脆鸡堡变成 Hold不住鸡排堡；`9900015187→9900013304`、
   `9900015188→9900015568` 同理）。旧编码已在映射表标 `retired` 并由 `build_pool` **强制排除**；
   新编码一律**独立核实、独立建条目**（带 `rotationFrom`），**不沿用**旧结论。
   `60001` 因此有**三个**成因（时段不供应 / 编码轮换 / 真失效），见 `MCP_INTEGRATION.md` 7.9。
5. **价格是门店级 + 时段级的。** 实测同一商品在 `3230019` 与 `3230442` 价格不同
   （如 `9900005456`：¥34 vs ¥33.5），且部分商品编码在门店间不一致 —— **核价记录不可跨店搬用**。
6. **菜单「现价」可能是条件价（已修复预筛）。** 在 106 项实时菜单中，`discountType` 为「随单购麦金卡优惠」的商品有 **17 个**
   （含 `9900000890`/`9900000891`/`9900016309`/`9900004236`/`9900011056` 等）：菜单现价 ¥28，
   但裸核价 **¥58**；`9900005321` 菜单 ¥62.9 而实付 **¥124.5**。
   2026-10-16（P1.9）已修复：预算预筛改用 `prefilterPriceYuan`——条件价商品用**原价**
   （26 条实测裸核价 == 原价，覆盖**两个时段**：午餐 16 条 = 11:25 那批 13 条 + P1.12 的 12:06 那批 3 条；
   早餐 10 条 = P1.13 用 `reservationDate` 预约取得的真实早餐菜单。17 个条件价商品里
    `521955 麦当劳联名徽章` 是周边非食品、被 `atomicNameRules` 排除在商品池外），
   无法确定无条件价的商品**不做本地预算判断**、交官方核价。
   **`calculate-price` 仍是唯一价格权威**；菜单价仍如实保留用于「菜单价 ≠ 官方价」差异记录。
   完整字段语义与证据见 `references/menu-price-semantics.md`。
   ⚠️ **2026-10-16（P1.10）补充**：无法本地判定价格的候选**不再与可信候选抢候选席位** ——
   候选选择优先占满「价格可判定」的席位，未定价候选只在剩余席位补齐；若所有候选价格都无法判定，
   输出会额外给出 `priceUndeterminedNotice`（说明"本地无法先行判断、这不等于无解"）。
   未定价候选仍**不被剪枝**（"未知 ≠ 超预算"）。
7. **`takeWayList` 随门店变化**：`3230019` 返回 `eat-in` + `take-in-store`，
   `3230442` 返回 `eat-in` + `locker-in`（店内取餐柜）。取餐方式**必须**取当前门店核价返回。
8. **优惠券路径尚未用真实券验证。** 本账号券包与门店券的官方返回**都是空的**，
   因此「真实带券核价」**仍未验证**。
   ⚠️ 2026-10-16 11:00 那批核价确实出现真实 `discount > 0`，但那是**店内促销自动生效**
   （`521986` 原价 ¥16 → 促销价 ¥11），**不是券**，不得当作"券链路已打通"。
   券相关逻辑的测试全部基于**明确标注来源**的样本（见 `tests/fixtures/coupons/README.md`）。
9. **未领取券无法提前评估。** `available-coupons` 不返回 `couponId`/优惠金额/门槛/适用商品，
   所以"领券前判断它能否省钱"**在当前接口下做不到**。
10. **饮料/小食的分类来自名称兜底规则**，未逐条调用 `query-meal-detail` 核实。它们只用于满足**可选偏好**，不参与硬性条件。
11. **「堡」包含鱼堡，但不支持蛋白偏好筛选。** 菜单把牛/鱼/肉同列为「堡」，所以 `双层深海鳕鱼堡`、`鱼排堡`
    也算汉堡。但「只要牛肉堡 / 不要鱼堡」这类偏好**当前无法筛选**：新条目只带了 `proteinType` 纯标注
    （不参与任何判定，有断言保证），且未回填到更早条目。用户提出蛋白偏好时必须如实说明。
12. **套餐按整份参与组合**，不支持拆解或替换子项；**需要用户多选的套餐**（如"堡堡随心拼"）一律不参与硬性条件。
13. **价格随门店与时间变化**。仓库里的测试快照只是历史记录，运行时一律重新拉取。
14. **"丰富度"是本产品自定义的排序规则**（有效件数 / 类别覆盖 / 预算利用率），**不是**营养学结论。
15. **不承诺"全网最低价"或"最划算"** —— 只在已确认的候选集合内比较。

### 哪些是已验证的，哪些不是

**已用真实 MCP 调用验证（到店链路）**
- 门店 → 菜单 → 餐品详情 → 核价 全链路
- `calculate-price` 返回字段：`originalPrice` / `discount` / `price` / `productList` / `takeWayList`
  （到店场景 `takeWayList[].code` = `eat-in` 堂食 / `take-in-store` 外带）
- 组合搜索与预算约束、核价失败与超预算的拒绝、无解提示、映射表对已知反例的排除
- **56 个映射条目的组成**（逐条 `query-meal-detail`，含 `evidence.at` 与 `storeCode`），其中 7 个已标 `retired`
- **第六批补齐 11 个「名称疑似含汉堡」的商品**（巨无霸、不素之霸双层牛堡、深海鳕鱼堡 / 巨无霸 / 不素之霸的 3·4 件套、
  鱼牛汉堡四件套随心选、鱼排堡开心乐园餐）→ 优先核实清单清空，锚点 25 → 36；
  11 条全部是**单选**结构，无需多选支持
- **时段切换行为**：早餐窗口内常规商品返回 `60001`；菜单切换晚于预约窗口起点；
  **跨门店价格与商品编码均存在差异**
- **商品编码轮换（7 组）**：含 4 组默认组成等价（如 `9900015162→9900008747`、`9900016054→9900016057`）
  与 3 组**同名但默认组成已变**（如 `9900015160→9900015602`）；另有 2 个编码因证据不足保持"当前不可验证"
- **第七批补齐 7 个「名称含堡但未核实」的商品**（2026-10-16 12:03–12:06，安格斯厚牛堡系列）：
  `511781 培根安格斯厚牛堡`、`511782 芝士安格斯厚牛堡`、`9900005428/9900005430`（三件套）、
  `9900000881/9900000882`（四件套）、`9900006957 安格斯厚牛堡四件套随心选`；
  7 条全部 `confidence = confirmed_detail` 且默认含堡 → 锚点 36 → **43**；
  其中 `9900006957` 虽名含「随心选」，但四个轮次**全为单选**且与 `堡堡随心拼（7件任选）` 的多选性质不同
- **条件价字段语义（16 个商品逐一裸核价）**：`discountType = 随单购麦金卡优惠` 的商品，
  裸核价**全部等于 `originalPrice`** 且 ≠ `currentPrice`；对照的「促销优惠」与无 `discountType`
  商品则等于 `currentPrice`。据此把预算预筛从菜单现价改为 `prefilterPriceYuan`
- **条件价现象**：17 个商品的菜单现价是「随单购麦金卡」条件价；
  实测 `9900000890`/`9900000891` 裸核价 **¥65.00**（菜单现价 ¥28），`9900005321` 实付 **¥124.5**（菜单 ¥62.9）
- **首个真实 `discount > 0`**：`521986 马苏里拉拉丝芝士条` 原价 ¥16 → 促销价 ¥11，
  官方返回 `originalPrice:3000 / discount:500 / price:2500`。**这是店内促销，不是券。**
- **券查询接口的真实返回**：`query-store-coupons` 返回 `data: []`（空）、
  `query-my-coupons` 返回"暂无可用优惠券"、`available-coupons` 返回 7 条**只有券名+状态**的记录
